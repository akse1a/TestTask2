# Платёжный мини-API с идемпотентностью · ДЗ №2

Вариант **C1** (финтех, уровень «для разработчиков»), формат — **соло**.
Небольшой HTTP-сервис на Go: создать платёж, повторить с тем же ключом идемпотентности,
получить статус, отменить. Собран по спецификации силами нескольких агентов.

Почему свой вариант из списка, а не свой проект: хотелось задачу, которая честно
раскладывается на **три независимые реализации одного контракта** — идеальный полигон
для субагентов и worktrees, а идемпотентность — классическое место, где агент пишет
правдоподобный, но неверный код.

---

## Как запустить

Нужен только **Go** (1.21+). Внешних зависимостей нет — сервис на стандартной библиотеке.

```bash
cd service
go run .
# сервер на http://localhost:8080 (порт можно задать переменной PORT)
```

Проверка живости:

```bash
curl -s localhost:8080/healthz
# {"status":"ok"}
```

> На машине, где `go env CC` указывает на кросскомпилятор, собирайте с `CGO_ENABLED=0 go run .`
> — сервис чисто на стандартной библиотеке, cgo ему не нужен.

### Примеры

```bash
# создать платёж (идемпотентно по заголовку Idempotency-Key)
curl -s -X POST localhost:8080/payments \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{"amount_minor": 10000, "currency": "RUB"}'

# повтор с тем же ключом и телом -> тот же платёж, HTTP 200 (второй не создаётся)
# тот же ключ, другое тело -> 409 idempotency_key_reuse

# статус
curl -s localhost:8080/payments/<id>

# отмена (повторная отмена идемпотентна)
curl -s -X POST localhost:8080/payments/<id>/cancel
```

Полный контракт (эндпоинты, статусы, коды ошибок, требования к конкурентности) —
в [docs/SPEC.md](docs/SPEC.md).

## Тесты

Юнит- и конкурентные тесты (в составе реализации):

```bash
cd service
CGO_ENABLED=0 go vet ./...
CC=gcc go test -race ./...        # или обычный go test ./..., если хочется без -race
```

Общий чёрно-ящичный conformance-набор (поднимает сервер и проверяет контракт по HTTP,
25 проверок включая 64-поточный тест идемпотентности):

```bash
CGO_ENABLED=0 python3 conformance/conformance.py service
```

## Как это делалось (агенты, worktrees, workflow)

Работа шла по повторяемой процедуре [workflows/spec-parallel-build.md](workflows/spec-parallel-build.md):

1. **Спека** контракта — `docs/SPEC.md`.
2. **Три worktree** (`impl-a/b/c`) и **три субагента параллельно**, каждый пишет свою
   независимую реализацию контракта (разные модели конкурентности) с тестами.
3. Общий **conformance**-набор прогнан против всех трёх — [reports/comparison.md](reports/comparison.md).
4. **Агент-ломатель** в отдельной сессии (не автор кода) — [reports/breaker.md](reports/breaker.md).
5. Выбрана лучшая (`impl-b`, слоистая), **смержена в main**, перенесена в `service/`.
6. Замер «последовательно vs параллельно» — [reports/measurement.md](reports/measurement.md).

Дословные промпты и решения — в [sessions/](sessions/). Итоговый отчёт по всем пунктам
задания (включая то, что **не** сработало) — в [REPORT.md](REPORT.md), он же собран
в PDF: [reports/report.pdf](reports/report.pdf).

## Структура репозитория

```
service/              — платёжный API на Go (main-реализация, impl-b)
docs/SPEC.md          — контракт v1.0
conformance/          — чёрно-ящичный набор проверок (Python, stdlib)
workflows/            — workflow «спека → веер → ломатель → сведение» + промпт
reports/              — сравнение, замер, отчёт ломателя, PDF
sessions/             — журнал сессий с дословными промптами
REPORT.md             — итоговый отчёт по пунктам задания
```

Ветки `impl-a`, `impl-b`, `impl-c` сохранены в истории — видно три параллельные работы
и их слияние.

## Секреты

В репозитории секретов нет. `.env`, `settings.json`, ключи — под `.gitignore`.
