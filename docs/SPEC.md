# SPEC · Платёжный мини-API с идемпотентностью

Версия контракта: **1.0**. Язык реализации: **Go** (стандартная библиотека `net/http`,
без внешних веб-фреймворков; хранилище — in-memory, потокобезопасное).

Это единый контракт. Три независимые реализации (A, B, C) должны его соблюдать так,
чтобы **один и тот же набор тестов проходил на каждой**. Всё, что не описано здесь, —
на усмотрение реализующего, но не должно нарушать описанное поведение.

---

## 1. Модель платежа

```
Payment {
  id:              string   // сгенерирован сервером, уникальный, напр. "pay_<hex>"
  amount_minor:    int64    // сумма в минорных единицах (копейки). СТРОГО > 0
  currency:        string   // ISO-4217, ровно 3 буквы A-Z. Поддержка: RUB, USD, EUR
  status:          string   // см. раздел 3
  idempotency_key: string   // ключ, с которым платёж был создан
  created_at:      string   // RFC3339 UTC
  updated_at:      string   // RFC3339 UTC
}
```

Деньги — **только целые минорные единицы** (`amount_minor`). Никаких float для сумм.
`123` = 1 рубль 23 копейки при `currency=RUB`.

---

## 2. Эндпоинты

Все тела запросов/ответов — `application/json; charset=utf-8`.

### 2.1 `POST /payments` — создать платёж

**Заголовки:**
- `Idempotency-Key: <string>` — **обязательный**. 1–255 символов. Отсутствие → `400`.

**Тело:**
```json
{ "amount_minor": 10000, "currency": "RUB" }
```

**Успех — `201 Created`:** объект `Payment` со `status: "created"`.

**Идемпотентность (ключевое требование):**
- Повторный `POST /payments` с **тем же** `Idempotency-Key` **и тем же телом**
  → `200 OK` и **ровно тот же** ранее созданный `Payment` (тот же `id`, тот же
  `created_at`). Второй платёж НЕ создаётся.
- Тот же `Idempotency-Key`, но **другое тело** → `409 Conflict`, код ошибки
  `idempotency_key_reuse`. Ничего не создаётся и не меняется.
- «Тело» для сравнения — нормализованная пара `(amount_minor, currency)`, а не побайтовое
  сравнение строки (порядок полей и пробелы не должны влиять).

**Ошибки валидации — `400 Bad Request`** (код в скобках):
- нет заголовка `Idempotency-Key` (`missing_idempotency_key`);
- `amount_minor` отсутствует, не целое, `<= 0` (`invalid_amount`);
- `currency` не из {RUB, USD, EUR} или не 3 буквы (`invalid_currency`);
- тело — не валидный JSON (`invalid_json`);
- неизвестные/лишние поля в теле допускаются к игнорированию, но не обязаны.

### 2.2 `GET /payments/{id}` — статус

- `200 OK` + объект `Payment`, если найден.
- `404 Not Found`, код `payment_not_found`, если нет.

### 2.3 `POST /payments/{id}/cancel` — отмена

- Платёж в статусе `created` → `200 OK`, `status: "canceled"`, `updated_at` обновлён.
- Платёж уже `canceled` → **идемпотентно** `200 OK` с тем же объектом (повторная отмена
  не ошибка).
- Платёж не найден → `404`, `payment_not_found`.
- (Статус `captured` в этой версии не вводится, поле для расширения — см. раздел 3.)

### 2.4 `GET /healthz` — проверка живости

- `200 OK`, тело `{"status":"ok"}`. Без побочных эффектов.

---

## 3. Статусы

```
created   → платёж создан (единственный стартовый статус)
canceled  → платёж отменён (терминальный)
```

Разрешённые переходы: `created → canceled`. Любой другой переход запрещён.
`captured` зарезервирован на будущее, но в v1.0 не реализуется.

---

## 4. Формат ошибок

Единый конверт для всех ошибок:
```json
{ "error": { "code": "invalid_amount", "message": "amount_minor must be > 0" } }
```
HTTP-статус соответствует таблице выше. `code` — из фиксированного списка:
`missing_idempotency_key`, `invalid_json`, `invalid_amount`, `invalid_currency`,
`idempotency_key_reuse`, `payment_not_found`, `method_not_allowed`, `not_found`,
`internal_error`.

Неподдерживаемый метод на существующем пути → `405`, `method_not_allowed`.
Неизвестный путь (не `/payments…` и не `/healthz`) → `404`, `not_found`
(отличается от `payment_not_found`, который относится к отсутствующему платежу
по существующему маршруту).

---

## 5. Конкурентность (обязательно к соблюдению)

Хранилище — потокобезопасное. Два **одновременных** `POST /payments` с одним и тем же
`Idempotency-Key` и одинаковым телом должны привести к **ровно одному** созданному
платежу; оба ответа ссылаются на один `id`. Гонки на этом месте — главный предмет
проверки агентом-ломателем.

---

## 6. Запуск и конфигурация

- Порт из переменной окружения `PORT`, по умолчанию `8080`.
- Точка входа: `go run .` в корне реализации поднимает сервер.
- Хранилище in-memory (перезапуск обнуляет данные) — это ожидаемо для v1.0.

---

## 7. Обязательные тесты (каждая реализация несёт свои)

Минимальный набор, который должен проходить (`go test ./...`):
1. создание платежа возвращает `201` и валидный объект;
2. повтор с тем же ключом и телом → `200`, тот же `id`, второй платёж не создан;
3. тот же ключ, другое тело → `409 idempotency_key_reuse`;
4. отсутствие `Idempotency-Key` → `400 missing_idempotency_key`;
5. `amount_minor <= 0` → `400 invalid_amount`; неверная валюта → `400 invalid_currency`;
6. `GET` существующего/несуществующего → `200` / `404`;
7. отмена `created` → `canceled`; повторная отмена → `200` идемпотентно;
8. конкурентный тест: N горутин с одним ключом → один платёж (используйте `-race`).

---

## 8. Definition of Done для реализации

- `go vet ./...` и `go test -race ./...` — зелёные;
- `go run .` поднимает сервер, `GET /healthz` отвечает `200`;
- в папке реализации — короткий `NOTES.md`: какие решения приняты, где сомнения,
  что НЕ доделано (честно).
